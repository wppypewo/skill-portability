Skill 可移植性實驗:一個 AI 流程導入的實作紀錄

附錄 A–E 見另一檔案《附錄》;原始輸出 35 筆見 zip 附件。

一、任務定義與研究問題

1.1 場景與問題來源

本報告處理一個具體的導入問題：一個在 Claude 上建立、測試過的提示詞工作流（以下沿用 Claude 生態的稱呼，叫它 skill），搬到免費版 Gemini 之後還剩多少效益？skill 不是模型，只是一份文件；把一份在 Claude 上運作良好的文件貼進另一個模型的指令欄，哪些東西跟著文件走、哪些留在原地，是本實驗真正要回答的問題。

場景來自課堂設定：導入對象是文組學生與資源受限的顧客，他們手上的工具是 Gemini 消費版 app。給這群人的導入建議若在別的環境（付費 API、AI Studio、其他模型）驗證，對他們並不成立；結論必須在他們實際使用的環境裡取得。因此本實驗把部署端固定在 Gemini app 的 Gems 功能，不用 AI Studio，也不用 API，此為硬性前提。

1.2 兩層假說

要回答上面的問題，得先拆開「skill 為什麼在 Claude 上有效」。本實驗採取的工作假說是：效益分兩層。

內容層：風格規則、詞彙表、正反範例。這些是寫在文件裡的知識：什麼詞不能用、什麼句式算翻譯腔、好譯文長什麼樣。知識以文字形式存在，理論上複製貼上就能帶走。

執行層：先讀完整份指令再動工、按宣告的步驟依序展開、輸出前逐項自檢、不跳步、不敷衍檢查表。這些是行為，不是文字。文件可以「要求」這些行為，但模型是否照做，取決於它有沒有被訓練成會認真對待這類指令。Claude 的 skill 機制連同其訓練是成對設計的；Gemini 收到同一份文字時，並無配套的行為訓練。

由此得到可檢驗的預測（此為假說，非既有事實）：移植後內容層大致存活，執行層衰減，表現為跳步驟、忽略檢查、格式漂移。

假說要成為「可檢驗」，執行層必須先變得看得見。為此 skill 強制每次輸出附帶一個處理說明區塊：辨識到的文體、選定的語域策略、以及與評分標準一一對應的十二項檢查表。模型若跳過流程、敷衍自檢，痕跡會落在這個區塊上：欄位缺漏、內容亂填、勾選與實際輸出不符，都是可逐項清點的證據。這個設計是整個實驗的觀測基礎，推理過程見第二節。

1.3 實驗設計總覽

先給全貌，細節分見第二、四、五節。

  • 任務：skill 名為 multilingual-style-transcreator，把法文文本轉換為繁體中文（台灣），使用者每次指定三種目標文體之一（文學翻譯、新聞體改寫、社群短文體），流程固定七步。
  • 測試文本：波特萊爾《巴黎的憂鬱》中的散文詩〈窗〉（Les Fenêtres），編號 T1，取自 Wikisource 公有領域版本。原規劃五篇（T1–T5，均已抓取歸檔），實際實驗僅用 T1 一篇跑完全部矩陣；僅用單一文本的限制在第六節說明。
  • 條件：五個。REF：Claude 搭配完整 skill，作為來源端參照，非部署端；A：SKILL.md 原文逐字貼入 Gem 指令欄；B：針對 Gemini 重寫的壓縮版；B'：壓縮版加回原版範例，用來隔離範例的作用；C：近零指令裸跑，作為 baseline。
  • 執行：本人擔任人工橋樑，在 Gemini app 手動建 Gem、貼文本、逐字複製輸出歸檔；每次執行開新對話，同條件盡量同日完成。每格重複二至三次。
  • 評分：rubric 分四類，風格忠實度 30、語域正確性 25、繁體中文自然度 25、格式與流程遵循 20；正式評分前定案。全部輸出打亂順序、遮蔽條件後盲評，評分完成才解盲。統計只做描述統計：平均分、分項對比、條件間差距。

二、Workflow 拆解

2.1 任務怎麼拆成七步

skill 的任務是把一篇法文文本依指定目標文體轉換成繁體中文。直覺的做法是一句話交代：「請把這篇翻成中文，風格要 X」。這種寫法多數情況也能出結果，問題在品質不穩定且錯誤無從歸因：譯壞了，不知道壞在理解、選詞還是文體判斷。

拆解的原則是照人類譯者的實際工作切，而非任意分段。一位譯者接到文體轉換委託，依序做的是：確認來源、讀懂文本質地（文體、語氣、句法、文化訊號）、鎖定不可動項（專有名詞、關鍵概念、數字）、決定策略（目標語域與在地化程度）、動手翻、對照檢查、修訂交稿。七步流程就是這條工作鏈的直接對應：

  1. 辨識來源語言、文本用途及讀者
  2. 分析原文文體、語氣、句法和文化訊號
  3. 提取專有名詞、關鍵概念及不可改動資訊
  4. 依指定目標文體選擇語域與在地化策略
  5. 完成第一版翻譯
  6. 逐項檢查語意、術語、語氣、格式與繁體中文習慣
  7. 修訂後輸出最終翻譯及處理說明區塊

這樣切分有兩個作用。其一，每步產出可單獨檢查：第 2 步的文體判斷、第 3 步的不變項清單都會落到處理說明區塊，錯誤能定位到步驟。其二，第 6 步（自檢）強制與第 7 步（輸出）分開：模型最容易省略的就是檢查，把它獨立成必經步驟，既是對執行層的直接施壓，也是後續量測的目標。

2.2 三種目標文體：壓力由低到高

目標文體選三種，刻意讓它們對執行層的壓力由低到高排開。

文學翻譯壓力最低：接近直譯，考驗意象與節奏的保留（不把圖像翻成含義、排比仍是排比）。原文結構即輸出結構，不需重組。

新聞體改寫壓力升高：資訊優先、順序可重排、主觀命題須加歸屬（「詩中主張……」）、抒情第一人稱轉為中性轉述。模型必須拆開原文再重組，同時記得每個命題都要交代出處。

社群短文體壓力最高：要壓縮（砍次要意象、只留最強鉤子）、斷行、口語，還要克制（表情符號至多一個、hashtag 至多兩個）。壓縮本身與「意象完整」檢查項直接衝突：模型得刪東西，又得在自檢時誠實交代刪了什麼。這是刻意設下的兩難，自檢誠實度在此最易現形。

事後看，這個排列的作用超出原先設計（詳見第五節）：它不只測出執行層的壓力反應，也測出內容層規則本身的品質差異。

2.3 可觀測性設計：讓執行層落到紙面

執行層行為（有沒有讀完指令、有沒有跳步、自檢敷不敷衍）本身看不見。要量它就得逼它留下痕跡。做法是強制每次輸出附帶固定格式的處理說明區塊，內含三欄位：

  1. 辨識到的文體（對應步驟 1–2 的產出）
  2. 選定的語域策略（對應步驟 4 的決策，須附二至三個具體決定）
  3. 檢查表逐項勾選結果（對應步驟 6，共十二項，每項必須標 ✓ 或 ✗，✗ 須附一行理由）

這個區塊是觀測窗口：欄位缺漏、內容抄模板、勾選與實際輸出不符，都是執行層失效的具體證據，可逐項清點，不依賴印象。

窗口要能量化，還需兩個配套。第一，規則全部編上識別碼（LIT-1、NEWS-3、LOC-4……），範例的違規標注、檢查表項目、評分時的扣分依據都引用同一套編號；移植後若失效，可定位到具體哪條規則，而非籠統說「格式跑掉了」。第二，十二項檢查表與 rubric 四大類一一對應（A 忠實度、B 語域、C 自然度、D 格式流程）。這使一個關鍵的量成為可測：模型自檢勾 ✓、人工評分卻判違規的次數。這個「宣稱與實際的落差」就是執行層誠實度的直接讀數，後續反覆用到。

2.4 提示詞結構的幾個決策

SKILL.md 定稿前有幾個結構性決定，記錄如下。

語言混合。規則本文用英文（遵循 skill-creator 慣例），輸出模板與檢查表用繁體中文，因為觀測對象是繁中輸出的欄位漂移，模板必須與輸出同語言。代價是文件成為英中混合體，跨語言指令理解成為一個未隔離變因，列入限制。

配對式範例。五組「同一段原文，一好一壞」的配對，反例逐條標注違反的規則編號。單給好例只教會模仿；好壞並陳且標注違規條目，規則才從抽象敘述變成可辨認的錯誤型態。五組覆蓋三文體加翻譯腔，各打一個最常見的失敗模式。

禁止事項獨立成節。「不得跳步」「不得省略處理說明」「不得在未驗證時勾 ✓」散在各節易被淹沒，集中成節是把執行層要求擺到最顯眼處。這一節在壓縮版（條件 B）被拆散併入各處，效果差異見第五節。

三、Skill 建構過程（含失敗迭代）

3.1 建構順序與紀律

建構照固定順序推進：規格先行 → SKILL.md 起草定稿 → rubric 在正式評分前逐項定案 → 使用者訊息模板凍結 → 執行。兩條紀律貫穿全程：失敗迭代一律保留（作廢輸出改標 _excluded 歸檔，不刪除）；每次改動記迭代日誌。本節取自這批日誌，依時序列出四類波折與一個方法學決定：前三類是流程與工程的失敗，第四類是 skill 內容本身的失敗，份量最重。

3.2 失敗迭代實錄

文本取得，三敗一勝。猜測 Wikisource 路徑全數 404；抓取工具的摘要模型以版權為由拒絕輸出公有領域文本（波特萊爾 1867 年即已過世，屬工具端過度謹慎）；抓原始碼只得到轉引標記。最後走 REST API 抓渲染後 HTML、自寫解析器成功，並與先前取得的兩篇短文逐字交叉驗證。教訓：來源與版本必須落到檔案層固定（metadata 記來源網址、版本、抓取日期）。

兩次靜默資料損壞。歸檔 Gemini 輸出時手工轉抄，把全形標點打成半形；標點正是評分項，改為腳本逐字節切片後人手不再碰內容。第二次出在自動化本身：盲測副本的「刪行首 # 符號」規則誤傷社群文體 hashtag 五筆，發現時已完成評分，記入限制。教訓：凡可程式化一律程式化；清洗規則是對當時見過的資料型態寫的，矩陣擴大時要跟著重審。

真實環境的干擾源。裸跑條件首次執行被執行者帳號的個人自訂指令接管，變成逐段確認模式並中止（見附錄 E，樣本 C-r1）；受同一干擾源影響，先跑的直接移植批次整批作廢重跑。計畫外觀察：有 Gem 指令的條件未被接管，空白介面被完全接管。含義是：部署 Gems 前應要求使用者檢查或關閉既有自訂指令。

社群文體規則寫錯方向（份量最重，數據見第五節）。社群規則（硬壓縮、斷行、限量口語詞）各條均可執行，盲評卻顯示：遵循得越徹底，產出離台灣讀者的網路語感越遠，評語是「完全不像網文」「不像真人寫的」。規則描述的是撰寫者想像中的網文，不是語料意義上的網文。這種失敗自檢永遠發現不了：規則錯了，自檢只會確認錯誤執行得很好；能揭露它的只有規則文件之外的判準，本實驗是人工盲評，實務上就是真人讀者。

3.3 誰來評分：一個中途的方法學決定

專案中途曾提議由 Claude 依 rubric 機械評分，否決理由三條：執行者對樣本不盲，等於讓提出假說者裁判自己的假說；參照組是 Claude 自己的輸出，自我偏好使結果不可信；核心觀測量「模型自檢通過、人工評分不通過」若由模型評，就退化成兩個模型的意見分歧，觀測窗口失效。最終以人工盲評為唯一評分來源，解盲後僅允許機械類核定（總分相加、格式欄依 rubric 機械定義）；評分者僅一人且為設計參與者，記入第六節限制。

四、移植過程與改動理由

4.1 三個移植版本

條件 A（直接移植）：SKILL.md 全文逐字貼入 Gem 指令欄，不做改寫。事前規則定為「超過指令欄上限即截斷貼入並記錄截斷點」，實際未觸發，全文 9,981 字元完整貼入。這本身是一個資料點：以本 skill 的體積，直接移植在 Gems 上沒有物理障礙，「貼不下」不構成改寫的理由。

條件 B（壓縮適配版）：針對 Gemini 重寫，3,665 字元，壓縮率約六成三。壓縮不是隨手刪，每項刪或留都記錄理由，完整決策表見附錄 C，原則三條：

  1. 刪敘述、留規則：frontmatter、目的說明等無行為約束力的文字全刪；
  2. 觀測窗口逐字保留：輸出模板與十二項檢查表一字不動，壓縮它等於破壞量測工具；規則編號（LOC-1 等）保留，因為檢查表逐字引用這些編號，刪了引用就對不上；
  3. 範例全刪：這是壓縮的預設行為，也刻意留作變因（見 B'）；與模板重複的「最終品質檢查表」章節一併刪除，同一要求只留一處。

條件 B'（壓縮+範例）：B 的全文加回原版五組配對範例，逐字拼接，5,192 字元。B 與 B' 唯一差異是範例的有無，用來隔離一個問題：範例屬於內容層知識，還是同時在支撐執行層行為。

4.2 執行協議

Gemini 端全部由本人手動執行：每次開新對話（避免前文污染）、同條件盡量同日完成（降低平台暗中切換模型版本的影響）、指令與文本逐字貼上、輸出逐字複製、逐筆記錄 metadata（日期、介面顯示模型、異常備註），依「條件-文體-文本-次別-日期」命名歸檔。介面模型全程標示「gemini 3.5 flash 延伸」，但無法保證各次落在同一版本，此為消費版環境的固有黑箱，記入限制。

Claude 參照組（REF）不在本對話脈絡內執行，而是每次啟動一個全新的隔離代理，只餵入 SKILL.md 全文與凍結版訊息，模擬 Gem 每次從零開始的狀態，避免實驗脈絡（rubric、假說、日誌）污染參照輸出。代價是執行方式與 Gem 並非完全相同（多一行「直接作答、不用工具」對齊指令），記入限制。

五、評測結果與假說驗證

5.1 評測設計摘要

評分四類配分：風格忠實度 30、語域正確性 25、繁體中文自然度 25、格式與流程遵循 20；每類從滿分起算，依事前定案的扣分觸發條件逐項扣分。忠實度另備可逐項核對的基準（文學格九項意象清單、新聞格九項命題清單、社群格鉤子與不變項），使盲評不退化為印象分。全部樣本去除條件標記、打亂順序後逐筆單獨評分，禁止並排比較，評分完成才解盲。Gemini 端每格二次、參照組三次（不對稱，記入限制）。解盲後僅做機械類核定（總分以分項相加為準、格式欄依 rubric 機械定義）；判斷類分數一律未動。

文學與新聞兩格型態一致：有 skill 的條件大幅領先裸跑（差距 28 至 43 分），直接移植損耗很小（文學格 REF−A 僅 5.7 分；新聞格 A 反高於 REF，屬小樣本波動，不過度解讀），壓縮有可見代價（新聞格 A−B 為 15 分）。社群格完全翻轉：裸跑最高，最守規則的參照組墊底，規則遵循度與分數呈反向。

5.3 五項發現

一，社群格翻盤。評分者對參照組社群輸出的備註是「完全不像網文」「太尷尬了，不像真人寫的」（見附錄 E，樣本 S-21、S-31）；對裸跑輸出反而多數無負評。結合第 3.2 節：skill 的社群規則寫錯方向，而規則遵循度最高的執行者受害最深。解讀候選（推論）：內容層與執行層不是獨立兩層，規則錯誤時，執行層的忠實度成為錯誤的放大器。

二，skill 效益在文學與新聞格大部分移植成功。內容層規則可觀察地改變了行為：參照組自述刻意避開禁用詞「重塑」，而未見過禁詞表的裸跑兩度使用它；裸跑在新聞格出現「不僅是……更是……」句式與抽象名詞堆砌（樣本 S-11、S-25），有 skill 的條件零出現。

三，執行層衰減是微侵蝕，不是崩塌。直接移植六次執行，模板骨架（兩區塊、三欄位、十二項勾選）全數存活；侵蝕出現在邊緣：詩題三次丟失、檢查表文字一次漂移（「七步驟」變「處理步驟」）、一次缺項（樣本 S-22）、勾選全數無逐項佐證（參照組每項附具體證據）。這些侵蝕全部低於盲評捕捉閾值：上述違規無一反映在扣分或「宣稱✓實際✗」計數中。

四，自檢誠實度的移植出現反直覺結果。參照組在社群格三次全數誠實自標 A1 ✗ 並附刪減理由（壓縮與意象完整衝突時，自檢反映衝突）；Gemini 端，壓縮版 B 同樣出現誠實 ✗ 附理由（新聞兩筆、社群一筆），完整版 A 卻全程勾 ✓，壓縮版比完整版誠實。解讀候選（推論，單格資料，假設級）：B 刪除了與輸出模板重複的檢查表章節，「檢查表只在一處」減少了規則稀釋，指令冗餘可能反而傷害遵循。

五，範例效果未被觀察到。B 與 B' 在文學格同為 90.0，逐筆分數型態相同；兩者的扣分點（過於文言、排比公式化）與範例針對的錯誤型態無關。只能結論「本格未觀察到範例效果」，不能結論範例無用：n=2，且測試格可能選錯了地方。

5.4 假說驗證

  • 內容層可移植：支持（文學、新聞格）。規則、禁詞表、輸出模板貼過去就生效，效益的主要部分跟著文件走。
  • 執行層衰減：方向對，型態錯，幅度預測錯。預測的是跳步驟、格式崩塌；實際是模板全數存活下的邊緣侵蝕，且幅度小到單人盲評察覺不到。「衰減」更準確的描述是：行為的形狀保留了，行為的內裡（逐項佐證、誠實的 ✗）變薄了。
  • 計畫外發現兩項（均標注為待檢驗假設）：內容層錯誤會被執行層忠實放大；指令冗餘稀釋遵循、單一事實來源提升自檢誠實度。

六、對 Harness 工程的新認識與限制

6.1 五條新認識

「假設級」表示僅單格資料支持，不應當作結論引用。

  1. 執行層可移植性高於預期：衰減是微侵蝕（丟詩題、措辭漂移、佐證消失），不是跳步驟或崩塌；模板骨架全數存活（本實驗內穩定重現）。
  2. 內容層與執行層互相作用：規則方向錯誤時，執行層越忠實結果越差（社群格 REF 60.0 對 C 80.0）；skill 的品質下限由規則正確性決定，不由執行力決定（單文體單文本，解讀候選）。
  3. 指令冗餘可能稀釋遵循：壓縮版刪除重複章節後，自檢誠實度反高於完整版（誠實 ✗ 三筆對零筆）。「同一要求只寫一處」可能勝過重複強調（假設級，最值得後續實驗）。
  4. 自檢誠實度是低成本探針：「誠實 ✗ 率」可從輸出直接讀出，免人工評分；給平台一個規則互相衝突的任務、看自檢敢不敢標 ✗，五分鐘測出它對 skill 的消化程度（能否用在其他任務待驗）。
  5. 環境干擾對空白介面的滲透力大於已載入指令的介面：個人自訂指令完全接管裸跑，未接管任何 Gem 條件（單一事件，解讀候選）。

6.2 實務建議：給文組使用者的 Gems 部署清單

  1. 指令先壓縮再貼：刪敘述留規則，同一要求只寫一處；體積不是問題，稀釋才是。
  2. 輸出模板與檢查表逐字保留：它是唯一的品管窗口。
  3. 先跑無指令 baseline：skill 不一定處處加分，社群格就是反例。
  4. 語感類規則風險最高：寫的常是想像中的語感，遵循越好偏得越遠；必須用真人讀者驗證，自檢救不了。
  5. 部署前請使用者關閉個人自訂指令，或確認不衝突。
  6. 同一批比較同日跑完，記下介面顯示的模型名稱，這是免費版唯一可做的版本控制。

6.3 限制

  • 單一文本：結論全數建立在〈窗〉一篇；T2–T5 未執行，文體壓力排序的結論可能與散文詩特性綁定。
  • 單人評分且評分者參與實驗設計：「宣稱✓實際✗」全程為零、而歸檔對照確認有漏，執行層侵蝕幅度可能被低估。
  • 樣本量：每格 n=2/3，不對稱；不做顯著性宣稱。
  • 版本黑箱：選消費版而非 AI Studio，因目標使用者用的就是 app，且 AI Studio 免費層對話會用於訓練，對課堂內容是實際障礙；代價是版本不可固定、不可嚴格重現。
  • 盲測不完全：模板有無部分洩漏條件；hashtag 清洗瑕疵影響五筆社群樣本。
  • 其他：解盲後允許機械類核定（判斷類分數不動）；參照組執行方式與 Gem 非完全相同；裸跑為近零指令而非零指令。

6.4 結語

一份在 Claude 上運作良好的 skill，貼到免費版 Gemini 後還剩多少？規則與知識大部分跟著文件走，文學與新聞格效益保留八成以上；行為的形狀也走了，內裡變薄——模板還在，佐證沒了，誠實的 ✗ 只在壓縮版倖存。而最重要的一課超出原問題：移植前更該問規則寫對了沒有，因為執行層是忠實的，它會把你的錯誤執行得和你的正確一樣好。
